# Task 8: Security Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:security-auditor` — [skills/security-auditor/SKILL.md](~/.claude/skills/security-auditor/SKILL.md)

## Description

Full-feature security audit of the JSON API scraper feature (Tasks 1–6).
Analysis only — read the source produced by the implementation waves and
write a security audit report. **Do not modify any code.**

This feature replaces a per-minute WKWebView DOM scrape with a direct
authenticated `URLSession` call to claude.ai's internal `/usage` endpoint,
reusing the session cookies already stored in
`WKWebsiteDataStore.default().httpCookieStore`. That makes session secrets
(`sessionKey`, `cf_clearance`, `__cf_bm`) flow through brand-new code
(`CookieBridge`, `UsageAPIClient`) that attaches them to outbound requests
and writes refreshed `Set-Cookie` values back into the shared store. The
single highest-risk failure mode for this feature is a session-credential
leak — into unified logging, into the on-disk debug file, or off-host via a
mis-scoped cookie or redirect.

The audit exists to enforce the security decisions made at planning time
(Decision 2 — host scoping; Decision 6 — secrets never touch the logs)
before the feature ships, rather than catching a leak after a release that
already exposed users' Claude sessions. It runs in the Audit Wave after
Task 6 completes, so all feature source exists and is wired together.

## What to do

1. Read all feature source created/modified in Tasks 1–6 (see Context
   Files), plus the existing logging surfaces (`AppLog`, `ScrapeDebugLog`)
   the new code logs through. Build a mental map of where the three session
   cookies originate, where they are attached to a request, and where they
   could be written out (log line, disk file, debug dump, error message).
2. Audit **cookie / secret handling** as the primary focus:
   - **No logging of secrets (Decision 6):** confirm no cookie value
     (`sessionKey`, `cf_clearance`, `__cf_bm`) or request header is ever
     emitted to `AppLog`. Confirm no token-adjacent field is interpolated
     into a log message with `privacy: .public` (the default for string
     interpolation in `os.Logger` — flag any cookie/header value that is
     not explicitly `.private`). Confirm any `.decodeFailed` repro dump is
     response-body-only and never includes the request, its `Cookie`
     header, or `Set-Cookie`. Confirm no cookie value reaches
     `ScrapeDebugLog` (which writes cleartext to disk).
   - **Host scoping (Decision 2):** confirm cookies are attached only to
     `claude.ai` requests (domain match), and that the redirect handler
     strips the `Cookie` header when a redirect leaves `claude.ai` — i.e.
     no secret is ever sent off-host. Confirm the `URLSession` carries no
     cookie jar of its own (`.never` / `httpShouldSetCookies = false` /
     `httpCookieStorage = nil`) so secrets are not silently persisted in a
     second, longer-lived store.
   - **No insecure transport / no cert bypass:** confirm there is no
     `URLSessionDelegate` that blindly accepts server trust
     (`.useCredential` on any challenge), no disabling of TLS validation,
     and no App Transport Security exception (check `Info.plist` /
     `Package.swift` for `NSAppTransportSecurity` /
     `NSAllowsArbitraryLoads`). All claude.ai traffic must be HTTPS with
     default validation.
   - **No secret persisted insecurely:** confirm the only thing written to
     `UserDefaults` is the org UUID (non-secret — acceptable). Flag any
     cookie value, header, or response body written to `UserDefaults`, a
     plist, or a plaintext file.
3. Run an **OWASP Top 10** pass over the new client surface, scoped to what
   applies to a local macOS menu-bar app calling one first-party endpoint:
   sensitive-data exposure (logs/disk — the main risk above),
   SSRF / off-host request (host scoping above), injection (the org UUID is
   interpolated into the request URL — confirm it is the decoded JSON value
   and cannot inject path/query, and that a hostile `/organizations`
   response cannot redirect the fetch off claude.ai), insecure
   deserialization (JSON decode of an untrusted internal response — confirm
   failures are caught and classified, not fatal), security
   misconfiguration (ATS, cookie jar), and improper error handling (errors
   surfaced without leaking secrets in their description).
4. Classify every finding by severity (critical / high / medium / low /
   info) with: the exact file and line, what is wrong, why it matters
   (the concrete leak/abuse), and a concrete fix. Map each finding back to
   the Decision it violates where applicable (Decision 2 / Decision 6).
5. Write the audit report to
   `work/api-scraper/logs/working/task-8/audit-report.md`. If zero issues
   are found, the report states that explicitly and lists each checked
   control with the evidence (file:line) that satisfies it — a clean audit
   must still show its work.

## Details

**Files:** Analysis only — this task writes exactly one artifact, the audit
report at `work/api-scraper/logs/working/task-8/audit-report.md`. No
source files are modified.

**Dependencies:** Depends on Task 6 (and transitively Tasks 1–5) — the
feature source must exist and be wired together before it can be audited.
Skill: `security-auditor`.

**Threat model (what we are protecting):** the user's live claude.ai
session. The three cookies `sessionKey`, `cf_clearance`, `__cf_bm` together
authenticate as the user; any one leaking to a place an attacker or a
support bundle can read (unified logging, the on-disk debug file, an
off-host request) is a session-takeover-grade exposure. This is why
Decisions 2 and 6 are load-bearing, not stylistic.

**Edge cases / specific things to look for:**
- A cookie or header value interpolated into a `Logger` call without an
  explicit `privacy:` qualifier — `os.Logger` treats interpolated strings
  as `.public`, so this silently writes the secret in cleartext. `AppLog`
  declares no privacy defaults, so the call site is the only guard.
- A `.decodeFailed` debug dump (mentioned in Decision 6) that dumps the
  whole `URLRequest`/`URLResponse` instead of just the response body —
  the request carries the `Cookie` header; the response carries
  `Set-Cookie`.
- `ScrapeDebugLog.write` receiving anything cookie-derived — it persists
  to disk in cleartext and survives across runs.
- A `urlSession(_:didReceive:completionHandler:)` server-trust delegate
  that calls `.useCredential` unconditionally, or
  `urlSession(_:task:willPerformHTTPRedirection:newRequest:completionHandler:)`
  that forwards the original headers without stripping `Cookie` when the
  redirect target host is not `claude.ai`.
- The org UUID coming from the decoded JSON and being string-interpolated
  into the `/organizations/{uuid}/usage` URL — confirm it is path-safe (a
  hostile value can't inject `../` or a different host) and that org
  discovery cannot point the fetch at an attacker-chosen host.
- `URLSessionConfiguration` that forgot one of
  `httpCookieAcceptPolicy = .never`, `httpShouldSetCookies = false`,
  `httpCookieStorage = nil` — any one missing means URLSession keeps its
  own cookie jar, drifting from the WebView store and persisting secrets in
  a second location.

**Implementation hints (process, not code):**
- Start by grepping the new files for `cookie`, `sessionKey`,
  `cf_clearance`, `Cookie`, `Set-Cookie`, `Authorization`, `.public`,
  `AppLog`, `ScrapeDebugLog`, `UserDefaults`, `AllowsArbitraryLoads`,
  `serverTrust`, `useCredential`, `Redirection` to find every relevant
  call site fast, then read each in context.
- Treat the audit as enforcement of Decisions 2 and 6: for each decision,
  either cite the line that honors it or file a finding that it's violated.
- If the implementation deviated from the spec in a way that affects
  security (e.g. introduced an independent cookie jar), call it out as a
  finding rather than assuming the spec was followed.
