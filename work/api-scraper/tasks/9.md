# Task 9: Test Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:test-master` — [skills/test-master/SKILL.md](~/.claude/skills/test-master/SKILL.md)

## Description

Full-feature **test quality audit** for the JSON-API-scraper feature. After
Tasks 1–6 land their unit and integration tests, this task reviews the whole
test suite holistically: does it actually cover the load-bearing behaviors the
tech-spec calls out, are the assertions meaningful (not vacuous), is the
`URLProtocol` stubbing wired correctly, and is the test pyramid balanced for a
size-M feature.

This is an **analysis-only** task. You read tests and source, then write a
single audit report. You do **not** modify code or tests — findings are handed
back for a follow-up fix cycle if needed.

The tech-spec "Testing Strategy" section is the contract you audit against. The
existing pre-API tests (`JSQuotaParserTests`, `QuotaParserTests`,
`ClaudeUsageTests`) are the idiom reference — the new tests should match that
house style (swift-testing `@Test` / `#expect`, fixed `now` seeds, exact-value
assertions, fixture-driven snapshots).

## What to do

1. Read the tech-spec "Testing Strategy" (unit + integration lists) and the
   per-task test expectations from Tasks 1–6. Build a checklist of every
   behavior that is supposed to be tested.
2. Read every test file the feature added under
   `App/Tests/ClaudeCounterTests/` (decode, mapper, classification,
   ISO-8601, `OrgIDStore`, `CookieBridge`, `UsageAPIClient`, orchestration,
   backoff) plus the source under test.
3. For each behavior in the checklist, mark it covered / partially-covered /
   missing, citing the test file and test name (or its absence).
4. Audit assertion quality: flag vacuous assertions (only `!= nil`, only
   "did not throw", spy-method-called without asserting end state). The
   fallback-orchestration tests in particular must assert `AppState.usage`
   end-state, **not** merely that a spy fired (tech-spec Integration tests +
   Decision 4/7).
5. Audit the `URLProtocol` stubbing: configuration is DI'd via a custom
   `URLSessionConfiguration` (not global `URLProtocol.registerClass`),
   path-based routing (`/organizations` then `/organizations/{uuid}/usage`)
   is correct and deterministic, degenerate bodies (Cloudflare "Just a
   moment…", login HTML, garbage JSON) are pinned as fixtures, and stubs
   don't leak across tests.
6. Audit test isolation: `OrgIDStore` tests run against an isolated
   `UserDefaults(suiteName:)` (never `.standard`); `CookieBridge` tests use a
   test-injected cookie store; no shared mutable state bleeds between tests.
7. Audit the secret-log guard test (Decision 6): a sentinel cookie value is
   driven through a captured log sink and asserted absent from every emitted
   line (header **and** body).
8. Audit the backoff test (Decision 7): asserts an **observable** (WebView
   never instantiated / fallback-invocation counter stays 0 across N ticks
   while logged-out), then a wake/window-open event clears the flag and
   re-probes.
9. Audit test-pyramid balance: for size M the strategy implies ≈9 unit / 4
   integration tests. Flag over-mocking, redundant tests, or missing layers.
10. Confirm the existing pre-API tests (`JSQuotaParserTests`,
    `QuotaParserTests`, etc.) remain present and green — the DOM-scrape
    fallback path must still be covered.
11. Write the audit report to
    `work/api-scraper/logs/working/task-9/audit-report.md` with: coverage matrix
    (behavior → test → status), assertion-quality findings, stubbing/isolation
    findings, pyramid-balance assessment, and a prioritized list of gaps
    (severity + suggested fix). Do not modify any code or test.

## Details

**Files:** None modified. Output is a new report at
`work/api-scraper/logs/working/task-9/audit-report.md` (create the `logs/working/task-9/` directory if absent).

**Dependencies:** Task 6 (depends_on: [6]) — orchestration tests must exist
before fallback/backoff coverage can be audited. Tasks 1–5 supply the
unit/integration tests this audit reads. Runs in the Audit Wave alongside the
Code Audit (Task 7) and Security Audit (Task 8); independent of those.

**Edge cases the audit must specifically check are tested:**
- 200 response whose body is the login HTML classified as `.notLoggedIn`
  (NOT `.decodeFailed`) — misclassification would trigger a needless DOM
  fallback instead of the Decision-7 backoff.
- `weekly_all` chosen over `weekly_scoped` for the weekly slot; missing
  `weekly_all` falls back to flat `seven_day`; empty `limits[]` with no flat
  fields → `.decodeFailed`.
- ISO-8601 `resets_at` parsed both with fractional seconds
  (`2026-06-17T13:49:59.900458+00:00`) and without — both yield the exact Date.
- `OrgIDStore` runs on an isolated `UserDefaults(suiteName:)`, never
  `.standard` (shared-state bleed between tests).
- Multiple-org `/organizations` fixture: active/first org chosen and cached.
- `percent` Double→Int truncation (e.g. `2.9` → `2`) matching `QuotaParser`.

**Implementation hints (for the auditor, not pseudocode):**
- Build the coverage matrix straight from the tech-spec's two bulleted lists
  (Unit tests / Integration tests) — each bullet is one expected behavior.
- The existing tests use swift-testing (`import Testing`, `@Test`, `#expect`)
  with a fixed `now = Date(timeIntervalSince1970: 1_700_000_000)` seed and
  exact-value assertions — the new tests should match. Flag any new test that
  uses loose assertions where an exact value is available (e.g. asserting a
  Date `!= nil` when the fixture timestamp is known).
- "Spy fired" vs "end-state asserted": for fallback orchestration the
  tech-spec explicitly requires asserting `AppState.usage` ends populated, not
  just that a fallback method was invoked. Treat a spy-only assertion there as
  a finding.
- For `URLProtocol`: a correct setup injects a custom
  `URLSessionConfiguration` with `protocolClasses` set (DI), not the global
  `URLProtocol.registerClass`, so stubs are scoped to the session and don't
  leak. Verify per-path routing and that the degenerate bodies are inline
  string/file fixtures.
- Note that the feature-level project-knowledge directory does not exist in
  this repo; there is no `patterns.md` Testing section to defer to — the
  tech-spec Testing Strategy and the existing test idiom are the standard.
