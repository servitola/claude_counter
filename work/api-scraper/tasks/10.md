## Description

Приёмочное тестирование фичи «JSON API scraper (drop per-minute WebView)» перед деплоем.
Это финальная волна: задачи 1–6 реализовали код, задачи 7–9 (code/security/test audit) уже
прошли. Здесь нужно прогнать полный набор качественных гейтов и проверить, что **каждый**
acceptance criterion из user-spec («How to verify») и tech-spec («Acceptance Criteria»)
действительно выполняется.

Это **НЕ** code-writing задача. Здесь ничего не пишется и не правится — только запуск
тестов и сборки, чтение результатов, и систематическая верификация критериев. Если что-то
не проходит — фиксируем как finding (severity + что сломано + где) и возвращаем фичу на
доработку, а не чиним сами.

Часть критериев (память в Activity Monitor, поведение с живой сессией claude.ai, реальный
403→WebView-refresh) автоматизировать нельзя — они Cloudflare-gated и недетерминированы.
Их помечаем как **deferred to post-deploy QA** с явным указанием, какой инструмент/действие
нужно для проверки на живом окружении (по Agent Verification Plan из tech-spec).

## Verification Steps

### Automated

Запускать из корня репозитория (`/Users/servitola/projects/services/claude_counter`):

- `make ci` → всё зелёное. Эквивалентно `make check` → `format-check lint test dead-code`.

Если нужно прогнать шаги по отдельности для локализации падения:
- `make test` → `swift test` — юнит + интеграционные тесты все проходят
- `make lint` → `swiftlint lint --strict` — без warnings/errors
- `make format-check` → `swiftformat --lint` — ничего не было бы переформатировано
- `make dead-code` → `periphery scan --strict` — нет мёртвого кода

### User

Следующие критерии требуют живого окружения (логин в claude.ai, Cloudflare, Activity Monitor)
и **детерминированно не автоматизируются** в pre-deploy. Помечаются как **deferred to post-deploy QA**
и проверяются по Agent Verification Plan tech-spec (инструменты: bash для `make`/запуска приложения
и `log stream`/Console для AppLog; Activity Monitor вручную):

- Logged-in: меню-бар показывает те же current %, weekly % и оба reset-time, что и claude.ai/settings/usage, обновляется каждую минуту, без инстанцирования WKWebView на нормальном тике.
- Память: steady-state RSS заметно ниже ~82 MB и нет per-tick WebContent/GPU helper-процессов.
- Resilience: после очистки `cf_clearance` происходит один WebView refresh, затем API-путь возобновляется (по логам AppLog).
- Auth: logout → graceful stop + login при открытии окна; login → возобновление.

**Files:** ничего не модифицируется. Задача только читает результаты сборки/тестов и спеки.

**Команда гейта:** `make ci` (подтверждено по Makefile: `ci: check`, `check: format-check lint test dead-code`). Все таргеты делают `cd App` внутри себя — запускать `make` из корня репозитория, не из `App/`.

**Маппинг критериев на доказательства:**
- US-3 / ISO-8601 reset-times, limits[]→ClaudeUsage маппинг (session→current, weekly_all→weekly, НЕ weekly_scoped), percent-truncation — покрыты юнит-тестами задач 1–2; вердикт берётся из их прохождения в `swift test`.
- US-2 / org-uuid discovery + cache + invalidate, выбор правильного org при нескольких — юнит-тесты задачи 3 (на изолированном `UserDefaults(suiteName:)`).
- US-4 / HTTP-классификация (403+challenge→needsCookieRefresh, 401/redirect/200-login-page→notLoggedIn, garbage JSON→decodeFailed) и fallback-оркестрация — юнит + интеграционные тесты задач 5–6.
- US-5 / logged-out backoff (Decision 7): нет re-входа в WebView на каждом тике — интеграционный тест задачи 6 (счётчик инстанцирований WebView = 0 за N тиков, затем wake/window-open сбрасывает флаг).
- Decode failure → DOM fallback (Decision 4): интеграционный тест оркестрации задачи 6.
- Decision 6 / no secrets in logs: secret-log guard интеграционный тест задачи 4/5 (sentinel cookie не появляется в логах).
- US-6 / память + no per-tick helpers: **deferred** (Activity Monitor, живое окружение).

**Findings:** если какой-то критерий FAIL — зафиксировать как JSON-подобный объект `{severity, issue, fix}` в отчёте; не чинить код самому. severity: blocker (критерий не выполнен / `make ci` красный) / major / minor.

**Edge cases:**
- `make ci` падает на `format-check`/`lint`/`dead-code`, а не на тестах — это всё равно FAIL последнего критерия tech-spec («lint/format/dead-code (`make ci`) clean»); фиксируем отдельно от тестового статуса.
- Отсутствует secret-log guard тест → это finding (Decision 6 не верифицирован), не «pass по умолчанию».
- Если какой-то «existing» тест (QuotaParser/JS) красный — fallback-путь сломан, blocker.

**Implementation hints:** не запускать приложение и не лезть в живую claude.ai-сессию в рамках pre-deploy — это область post-deploy QA. Здесь только статический/тестовый гейт + аудит критериев по артефактам.
